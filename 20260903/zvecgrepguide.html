01한 줄 정의

"Know the words—or don't. Just zg."

zg는 정확한 단어를 알면 rg처럼, 모르면 의미로 찾게 해주는 검색 도구다. 원래 세 도구로 나뉘어 있던 일, 즉 정규식 완전탐색(ripgrep), 키워드 랭킹(BM25 전문검색), 임베딩 의미검색(벡터)을 하나의 인덱스와 하나의 명령으로 합쳤다. 대상은 코드만이 아니라 Markdown, 텍스트, CSV/JSON/YAML 같은 비코드 파일까지다.

설계 원칙 두 가지가 문서 전체를 관통한다. 첫째 로컬 우선: 파일, 인덱스, 로컬 모델은 기계 밖으로 나가지 않고, 리모트 임베딩(Qwen API)만 명시 승인 후 데이터가 나간다. 둘째 에이전트 친화: 기본 출력이 미리보기 없는 압축 형식이라 LLM 컨텍스트에 넣는 토큰이 적고, MCP로 붙이면 에이전트가 프롬프트에 도구 이름을 안 써도 알아서 호출한다.

# 원본(Node) 기준 최소 사용법
npm install -g @zvec/zvec-grep
zg index --embedding local/potion-retrieval-32m
zg query --human "where theme preferences are restored" --limit 3
zg install --target qwen --yes   # Qwen Code에 MCP 자동 등록

02구조

진입점은 둘, 엔진은 하나, 검색 경로는 둘.

경로잘 맞는 질문데이터 소스
인덱스 검색의도, 관련 개념, 랭크된 키워드워크스페이스 인덱스의 BM25/FTS + 벡터
managed ripgrep알고 있는 문자열, 심볼, 경로, 정규식파일을 직접 스캔(임베딩 모델 불필요)

신뢰 경계도 명확하다. 리포지토리 인덱스는 <workspace>/.zvec-grep/, 전역 설정과 데몬 상태는 ~/.zvec-grep/, 로컬 모델 캐시는 ~/.zvec-grep/models. 서버는 loopback에만 리슨하고 MCP 엔드포인트는 Bearer 인증으로 막는다. 단 이 Bearer 인증은 로컬 엔드포인트 보호용이지 리모트 임베딩 데이터 전송을 허가하는 게 아니다. 그 허가는 별도 절차(--allow-remote 또는 zg auth grant)다.

03인덱싱 파이프라인

workspace → 파일 발견 → 로컬 인덱스 → 쿼리 라우트 → 압축 결과

zg index는 리포지토리 루트에서 돌린다. .git과 .zvec-grep은 항상 제외되고, 의존성·빌드·캐시·로그 디렉터리와 ignore 파일에 걸리는 것들은 기본 제외다. 범위는 ripgrep과 같은 문법으로 좁힌다: -g "src/**" -g "!dist/**" -t ts --max-filesize 500K --hidden --no-ignore. 파일 타입 필터는 glob 뒤에 적용되므로 -g "docs/**" -t ts는 docs 안의 TypeScript만 고른다.

명시적 --max-filesize가 없으면 타입별 안전 한도가 적용된다: 코드 1 MiB, 텍스트·Markdown 256 MiB, 구조화 데이터 16 MiB, 이미지 10 MiB. 한도로 빠진 파일은 조용히 스킵되며 zg index --debug로만 개수와 샘플을 볼 수 있다.

인덱스 유지

새 인덱스의 모델은 --embedding → 환경변수 ZVEC_GREP_EMBEDDING → 전역 기본값 순으로 결정된다. 기존 인덱스는 저장된 모델·파일 선택 설정을 재사용하므로 두 번째부터는 zg index만 치면 증분 갱신이다. 모델을 바꾸면 벡터 공간이 달라지므로 --rebuild가 강제되고, 삭제는 zg index --drop --yes로만 된다. 상태는 zg status(루트, 모델, 파일 수, 실패, truncation 수, 다음 권장 동작)로 본다. 검색 결과에는 fresh / possibly_stale 신선도가 붙는다.

위치 인자 하나만 주면 하이브리드. 나머지는 통제가 필요할 때만.

ranked sample

정확한 용어를 인덱스 안에서 BM25 랭킹.

ranked sample

렉시컬 없이 개념적 유사도만.

ranked sample

exhaustive
zg query "where theme preferences are restored"      # 기본 = hybrid
zg query --fts "AuthService"
zg query --vector "where credentials are validated"
zg query --hybrid "authentication flow" --fts "ForbiddenError" --fuse --limit 10
zg query --rg -n -F "AuthService" -g "*.ts" src     # ripgrep 그대로
zg query "plugin lifecycle" --preview short --limit 5  # 에이전트용 압축 출력

여러 쿼리 그룹은 --fuse를 안 주면 그룹별로 따로 나온다. 융합은 소스 기준 src/engine/pipeline/search/index.ts의 RRF_K = 60, score += 1 / (RRF_K + rank), 즉 표준 Reciprocal Rank Fusion이다. managed rg는 ripgrep의 매칭·컨텍스트(-A/-B/-C)·엔진·인코딩·glob·타입 옵션을 받지만, zg가 결과 형식을 소유하므로 --json, --count, --files, -l, -o, --replace, --vimgrep 같은 출력 변경 옵션은 거부된다.

리모트 임베딩 승인 절차

zg config provider set qwen --api-key "$DASHSCOPE_API_KEY"   # 자격증명 = 접근권한
zg index --embedding qwen/text-embedding-v4 --allow-remote      # 이 명령 한 번만 전송 허가
zg auth grant --capability embedding --scope workspace \
  --embedding qwen/text-embedding-v4                            # CLI+MCP 공유 워크스페이스 grant
zg auth status / zg auth revoke

자격증명과 데이터 전송 허가를 분리한 점이 핵심이다. MCP 경유 검색에서 리모트 모델이 걸리면 서버가 elicitation/create로 승인을 요청하고, 그게 안 되는 클라이언트(Qoder)는 AskUserQuestion/ask_user_question 툴로 "워크스페이스 승인 / 로컬 FTS만 / 취소" 세 가지를 묻는다. 헤드리스 세션은 절대 자동 승인되지 않는다.

07벤치마크 주장

A/B 페어: 과제·모델·프롬프트·환경·제한 동일, zg 접근 여부만 다름.

SWE-QA-Bench는 Claude Code + Claude Opus 5(high reasoning), BrowseComp-Plus는 Codex + gpt-5.6-sol(medium)로 돌렸고, zg 프로필은 둘 다 Qwen3.7 Text Embedding을 썼다. 주장은 입력 토큰, 툴 호출 수, 에이전트 소요시간 감소와 답변 품질 유지·향상이다. 실제 수치는 README에 SVG 그래프로만 들어 있어 이 문서에는 옮기지 못했다. 사례 연구는 Pylint(AST 노드 처리 분기), Matplotlib(FontInfo가 math-text 렌더링 단계를 지나는 흐름), Django(username 유일성 · ORM 트랜잭션 · formset bulk)의 리포지토리 이해 과제다.

주장의 논리는 단순하다. 의미검색이 탐색 공간을 좁히고, 랭크된 렉시컬 검색이 정확한 식별자를 고정하며, 압축된 증거가 넓은 스캔·반복 호출·컨텍스트 소모를 줄인다는 것. 코드는 심볼·시그니처·breadcrumb로, 산문은 섹션·청크로 인덱싱되므로 같은 루프가 도메인을 가리지 않는다는 게 "일반화" 근거다.

08파이썬으로 쓰기

앱은 TypeScript 38k 라인이지만, 엔진은 파이썬 wheel로 이미 있다.

결론

zvec-grep의 스토리지 엔진 @zvec/zvec와 같은 C++ 코어가 PyPI zvec 0.7.0으로 배포된다(manylinux_2_28 x86_64, Python ≥ 3.9, 의존성은 numpy 하나). FTS(BM25)와 벡터 인덱스, RRF 리랭커까지 파이썬 API로 노출돼 있어서 옮길 것은 엔진이 아니라 그 위의 청킹·라우팅·출력 로직이다. 아래 프로토타입은 이 세션에서 실제로 실행해 결과를 확인했다.

검증된 프로토타입

zg_min.py✓ zvec 0.7.0 / Python 3.11에서 실행 확인

import zvec, numpy as np, shutil

DIM = 1024  # qwen3-embedding-0.6b 기준. 테스트는 8차원 랜덤 벡터로 돌림

# 1) 스키마: 스칼라 필드(path, line) + FTS 필드(content) + 벡터 필드(emb)
schema = zvec.CollectionSchema(
    name="workspace_index",           # 영문/숫자/밑줄만 통과
    fields=[
        zvec.FieldSchema("path", zvec.DataType.STRING),
        zvec.FieldSchema("line", zvec.DataType.INT64),
        zvec.FieldSchema("content", zvec.DataType.STRING,
            index_param=zvec.FtsIndexParam(tokenizer_name="ngram",   # 한국어는 ngram 또는 jieba
                                          filters=["lowercase"])),
    ],
    vectors=[zvec.VectorSchema("emb", zvec.DataType.VECTOR_FP32, DIM,
        index_param=zvec.HnswIndexParam(metric_type=zvec.MetricType.COSINE))],
)
coll = zvec.create_and_open("./.zg-py", schema)   # 두 번째부터는 zvec.open()

# 2) 청크 적재 (id에 ':' '.' 불가 → 치환)
def doc_id(path, line): return f"{path}_{line}".replace(".", "_").replace("/", "__")
coll.insert([
    zvec.Doc(id=doc_id(p, l), fields={"path": p, "line": l, "content": c},
             vectors={"emb": embed(c)})
    for p, l, c in chunks            # chunks = 청킹 단계 출력
])

# 3) 두 경로 질의 → RRF 융합 (zg와 동일: k=60, 1/(k+rank))
def hybrid(q, topk=10, k=60):
    fts = coll.query(zvec.Query(field_name="content", fts=zvec.Fts(match_string=q)),
                     topk=topk, output_fields=["path", "line"])
    vec = coll.query(zvec.Query(field_name="emb", vector=embed(q)),
                     topk=topk, output_fields=["path", "line"])
    score, seen = {}, {}
    for hits in (fts, vec):
        for rank, d in enumerate(hits, 1):
            score[d.id] = score.get(d.id, 0) + 1 / (k + rank); seen[d.id] = d
    return [seen[i] for i, _ in sorted(score.items(), key=lambda x: -x[1])][:topk]

테스트 결과: 한국어 쿼리 "데드락"에 대해 FTS 경로가 ngram 토크나이저로 detect_oht_deadlock … 데드락 감지 청크를 정확히 잡았고, 벡터 경로 3건과 RRF로 합쳐진 최종 순위에서 같은 청크가 1위(0.0328)로 올라왔다. 즉 zg의 hybrid 라우트가 파이썬 30줄로 재현된다.

나머지 조각

# embed(): 로컬 GGUF (zg의 local/qwen3-embedding-0.6b와 동일 모델)
from llama_cpp import Llama

# --rg 라우트: ripgrep 바이너리 그대로
import subprocess, json
def rg(pattern, root, *opts):
    out = subprocess.run(["rg", "--json", *opts, pattern, root], capture_output=True, text=True).stdout
    return [json.loads(l)["data"] for l in out.splitlines() if '"type":"match"' in l]

from tree_sitter_languages import get_parser
parser = get_parser("python")
def code_chunks(path, src):
    tree = parser.parse(src.encode())
    for n in tree.root_node.children:
        if n.type in ("function_definition", "class_definition"):
            yield path, n.start_point[0] + 1, src[n.start_byte:n.end_byte]

원본에 없는데 파이썬에서 바로 되는 것: PDF/xlsx 추출(pdfplumber, openpyxl), Logpresso 쿼리·MCS 로그 패턴·알람 코드표 같은 도메인 청커, Oracle/MongoDB 레코드를 청크로 직접 적재하는 경로.

반입 시 주의점

  • wheel 호환: zvec는 manylinux_2_28 x86_64 빌드다. 대상 서버 glibc ≥ 2.28 확인, 파이썬 버전별(cp39–cp313) wheel을 맞춰 받을 것.
  • 이름 제약: 컬렉션 이름은 정규식 검사를 통과해야 한다(ws는 실패, workspace_index는 통과). 문서 id에 :와 .가 들어가면 "contains invalid characters"로 insert가 거부된다. 경로 기반 id는 치환해서 쓴다.
  • 한국어 FTS: 기본 standard 토크나이저 대신 ngram 또는 내장 jieba를 써야 한글 부분 일치가 된다. 프로토타입은 ngram으로 확인.
  • 인덱스 호환: 원본의 files.zvec/index.zvec를 파이썬에서 열려면 스키마를 맞춰야 하므로, 처음부터 파이썬 쪽 스키마로 새 인덱스를 만드는 게 깔끔하다.
  • 모델 교체 = 재빌드: 원본과 같은 이유로 임베딩 모델을 바꾸면 벡터 필드 전체를 다시 넣어야 한다. 차원이 같아도 공간이 다르다.
