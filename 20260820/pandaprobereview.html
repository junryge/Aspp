02 — What it is

이게 뭔데

Chirpz AI가 만든 오픈소스 에이전트 엔지니어링 플랫폼. 에이전트가 돌면서 남긴 실행 기록(트레이스)을 모으고, 그걸 LLM 심판으로 채점해서, 어느 단계에서 어떻게 망가졌는지 대시보드로 보여준다.

01계측SDK 데코레이터·래퍼로 LLM 호출과 툴 호출을 전부 span으로 기록
02수집FastAPI가 받아 Redis 큐에 적재 → Celery 워커가 PostgreSQL에 영속화
03채점LiteLLM으로 LLM-as-a-judge 실행 → 지표별 0~1 점수 + 사유
04추적대시보드에서 세션·트레이스·스팬 단위로 실패 지점 역추적

구성 서비스

서비스내용포트
frontendNext.js 대시보드3000
appFastAPI 애플리케이션 서버 API 레퍼런스: /scalar8000

붙일 수 있는 프레임워크

여기가 핵심이다. OpenAI 래퍼와 LiteLLM 래퍼가 있다는 건, 사내 vLLM(Qwen3 등) OpenAI 호환 엔드포인트를 쓰는 에이전트도 코드 한 줄로 계측된다는 뜻이다. 외부 상용 모델을 안 써도 계측 자체는 그대로 성립한다.

03 — Fit

우리 문제와의 매핑

"에이전트가 제대로 대답을 못한다"는 현상 하나지만, 원인은 보통 넷 중 하나다. PandaProbe의 지표는 이 넷을 각각 분리해서 짚는다.

엉뚱한 툴을 부른다물어본 건 반송 이력인데 설비 마스터를 조회한다
Tool Selection — 사용 가능한 툴 목록과 실제 호출을 대조해서 과선택·미선택·오선택을 0~1로 채점
툴은 맞는데 인자가 틀린다HID는 맞는데 기간이나 FAB 코드를 잘못 넣는다
Tool Call Accuracy — 호출 하나하나에 yes/no 판정 + 사유. 어느 인자가 왜 틀렸는지가 남는다
빙빙 돌다가 끝난다같은 조회를 세 번 하고 결론을 못 낸다
Step Efficiency — 중복 스텝·불필요 호출·투기적 시도에 감점. 우유부단함이 점수로 찍힌다
계획은 세우는데 안 지킨다3단계로 하겠다 해놓고 1단계만 하고 답한다
Plan Adherence — 트레이스에서 계획을 추출해 실행 순서·완결성과 대조
결국 답을 못 했다말은 그럴듯한데 요청을 충족 못 함
Task Completion — "successfully" 같은 주관적 표현을 배제하고 사실 기술만 추출해서 충족도 채점
가끔만 터진다평소엔 되는데 특정 케이스에서만 무너진다
Agent Reliability / Consistency — 세션 단위로 최악값(tail risk)과 분산을 따로 본다

지금 "AMOS 쪽 에이전트가 대답을 못한다"는 얘기는 이 여섯 중 어느 건지 아직 특정이 안 된 상태다. PandaProbe를 붙이는 목적이 바로 그 특정이다. 붙이고 하루만 돌려도 어느 지표가 바닥인지 나온다.

04 — Scoring

채점은 어떻게 되나

전부 LLM-as-a-judge다. 다만 한 방에 점수를 뱉는 게 아니라 추출 → 판정 → 사유로 단계를 나눠서, 심판 모델이 트레이스에 없는 걸 지어내지 못하게 묶어놨다.

지표단계산출
Task Completion과업/결과 사실 추출 → 충족도 채점verdict 0–1 + reason
Tool Selection목표·호출툴·가용툴 추출 → 선택 품질 채점score 0–1 + reason
Tool Call Accuracy호출별 인자 추출 → 개별 yes/no → 종합 사유verdicts 리스트
Step Efficiency과업 추출 → 최소성 기준 채점score 0–1
Plan Adherence과업 추출 → 계획 추출 → 순서/완결성 대조score 0–1
Agent Reliability세션 내 최악 트레이스 중심 (max-compose + top-k)0–1 0.3 미만이면 치명적 실패 포함
Agent Consistency세션 내 편차 중심 (가중 RMS)0–1 신뢰도 신호 필요

실행 방식은 UI에서 수동 실행, API 호출, 스케줄링(Celery Beat) 세 가지다. 야간 배치로 전날 트레이스를 통째로 채점시키는 운영이 가능하다.

05 — Blockers

폐쇄망 3대 블로커

기본값이 전부 클라우드를 향해 있다. 다행히 셋 다 설정으로 돌릴 수 있게 코드가 짜여 있는데, 3번은 보안 심의가 필요하다.

① Docker 필수

중

start.sh + docker-compose.yml이 유일한 공식 자체호스팅 경로다. 서비스 6개(frontend / app / worker / beat / postgres / redis)를 컨테이너로 띄우는 구조. 우리 운영망은 Docker·Node.js가 없다.

우회

A안 — 이미지를 외부에서 docker save로 tar 반입 → 반입 서버에서 docker load. Docker가 있는 서버가 한 대라도 있으면 가장 깔끔하다.
B안 — Docker 없이 개별 구동. backend는 pyproject.toml 기반 pip 설치라 FastAPI + Celery worker/beat를 직접 띄울 수 있고, PostgreSQL 16 / Redis 7은 사내 인스턴스를 물리면 된다. 문제는 frontend만 Next.js 빌드가 필요하다는 것 — 외부에서 빌드 산출물을 반입하거나, 1단계에서는 대시보드 없이 API + /scalar만 쓰는 축소 운영도 성립한다.

② 기본 인증이 Supabase / Firebase

상

AUTH_PROVIDER 기본값이 "supabase"다. Firebase도 선택지인데 둘 다 외부 IdP라 폐쇄망에서 아예 동작하지 않는다.

우회

AUTH_ENABLED=false로 두면 DevelopmentAdapter가 붙어서 외부 IdP를 전혀 호출하지 않고 고정 개발자 계정으로 통과시킨다. 즉 기술적으로는 해결된다.
다만 이건 코드 주석에도 "local development" 전용으로 명시돼 있고, 인증이 사실상 무력화되는 상태다. 프로덕션으로 쓰려면 앞단에 사내 SSO 리버스 프록시(예: Nginx + 사내 인증)를 두고 서버는 망 내부로만 노출하는 구성이 전제다. 보안 심의 대상으로 잡아야 한다.

③ 평가 모델 기본값이 Vertex AI Gemini

하

EVAL_LLM_MODEL 기본값이 vertex_ai/gemini-3.1-flash-lite, 임베딩은 vertex_ai/text-embedding-004. 그대로 두면 채점할 때마다 외부로 나간다.

우회

모델 문자열이 LiteLLM 포맷(<provider>/<model>)이라 openai/…로 바꾸고 OPENAI_API_KEY에 더미값, base URL을 사내 vLLM OpenAI 호환 엔드포인트로 지정하면 된다. 설정 코드에 "쓸 provider의 키만 설정하면 나머지는 알아서 건너뛴다"고 명시돼 있다. 임베딩 모델도 같이 바꿔야 한다는 것만 놓치지 말 것.

④ (추가) Harness는 CLI를 통해서만 동작

중

자가수리 루프인 pandaprobe-harness는 플랫폼 접근을 전부 pandaprobe CLI에 위임한다. 공식 설치법이 curl -fsSL https://cli.pandaprobe.com/install.sh | sh — 폐쇄망에서 그대로는 안 된다. CLI 바이너리 오프라인 반입과 엔드포인트 지정 가능 여부를 별도 확인 필요. 그래서 Harness는 3단계로 미룬다.

⑤ (추가) 외부 SaaS 키 항목들

하

설정에 Stripe(결제), Resend(메일), Attio(CRM), PostHog(제품 분석) 키 항목이 들어 있다. 클라우드 서비스 운영용이라 키를 비워두면 비활성이지만, 폐쇄망 반입 전에 PostHog 텔레메트리가 정말 키 없이 조용한지는 코드로 한 번 확인하고 넘어가는 게 맞다.

06 — Rollout

도입 절차

한 번에 다 넣지 말 것. 폐쇄망 부담이 낮은 순서대로 3단계로 끊는다. 1단계만 해도 "왜 대답을 못하는지"의 답은 나온다.

  1. SDK만 먼저 붙인다 — 부담 최소

    서버 없이도 계측 코드는 먼저 넣을 수 있다. PANDAPROBE_ENABLED=false면 전부 no-op이라 운영에 영향이 없다. 휠 파일을 오프라인 반입해서 pip install하고, 에이전트 진입점에 데코레이터/래퍼만 건다.

    산출: 계측된 에이전트 코드 + 반입한 wheel 목록.

  2. 수집 서버를 망 내부에 세운다

    Docker 반입이 되면 A안, 안 되면 B안(pip 직접 구동 + 사내 PostgreSQL/Redis). AUTH_ENABLED=false + 앞단 사내 인증 프록시. 대시보드 빌드가 막히면 API + /scalar만으로 시작한다.

    산출: PANDAPROBE_ENDPOINT로 물릴 사내 URL 하나.

  3. 평가 모델을 사내 LLM으로 갈아끼운다

    EVAL_LLM_MODEL·EVAL_EMBEDDING_MODEL을 사내 vLLM 엔드포인트로. 이 시점부터 채점이 돌기 시작한다. 야간 배치(Celery Beat)로 전날 트레이스 일괄 채점.

    산출: 지표별 baseline 점수 — 여기서 "무엇이 문제인지"가 확정된다.

  4. 1주 돌리고 판정한다

    Task Completion / Tool Selection / Tool Call Accuracy 중 어느 게 바닥인지 본다. 바닥인 지표가 곧 수정 방향이다. 프롬프트 문제인지, 툴 스키마 문제인지, 모델 체급 문제인지가 여기서 갈린다.

  5. (선택) Harness로 자가수리 루프를 건다

    CLI 오프라인 반입이 확인된 뒤에만. 처음엔 반드시 observe_only=True로 — 룰을 쓰지 않고 관찰만 한다. 여기까지 오면 에이전트가 스스로 실패를 진단하고 운영 룰을 축적한다.

07 — Code

붙이는 코드

설치 (오프라인 반입 기준)

# 외부망에서 휠 내려받아 반입
pip download pandaprobe -d ./wheels
# 필요한 어댑터만 골라서 (langgraph / openai / anthropic / crewai …)
pip download "pandaprobe[openai,langgraph]" -d ./wheels

# 폐쇄망 내부
pip install --no-index --find-links=./wheels "pandaprobe[openai,langgraph]"

환경변수 — 자체호스팅 기준

PANDAPROBE_ENDPOINT=http://pandaprobe.내부도메인:8000   # 이거 빠지면 외부로 나간다
PANDAPROBE_API_KEY=pk_...
PANDAPROBE_PROJECT_NAME=amos-agent
PANDAPROBE_ENVIRONMENT=production
PANDAPROBE_RELEASE=v1.0.0

# 운영 튜닝 (기본값)
PANDAPROBE_BATCH_SIZE=10          # flush 배치 크기
PANDAPROBE_FLUSH_INTERVAL=5.0     # 백그라운드 flush 주기(초)
PANDAPROBE_MAX_QUEUE_SIZE=1000    # 가득 차면 오래된 것부터 버림 + 경고 로그
PANDAPROBE_ENABLED=true           # false면 전부 no-op — 롤백 스위치
PANDAPROBE_DEBUG=false

PANDAPROBE_ENDPOINT 기본값은 https://api.pandaprobe.com다. 이 값을 안 넣으면 사내 트레이스가 외부로 나간다. 반입 검증 항목 1번으로 잡을 것.

환경변수는 클라이언트 초기화 시점에 os.environ.get()으로 한 번만 읽는다. 이후 변경은 반영 안 되니 재설정하려면 pandaprobe.init()을 다시 부른다.

사내 vLLM(OpenAI 호환) 에이전트 계측

from pandaprobe.wrappers import wrap_openai
from openai import OpenAI

# 사내 vLLM 엔드포인트를 그대로 감싼다
client = wrap_openai(OpenAI(
    base_url="http://내부-vllm:8000/v1",
    api_key="dummy",
))

resp = client.chat.completions.create(
    model="Qwen3-...",
    messages=[{"role": "user", "content": "M16A HID 37 반송 지연 원인은?"}],
)

직접 만든 루프 계측 (데코레이터)

import pandaprobe

@pandaprobe.trace()          # 한 턴 = 하나의 트레이스
async def handle_question(q: str) -> str:
    plan = await make_plan(q)
    return await execute(plan)

@pandaprobe.span()           # 툴 호출 하나 = 하나의 스팬
def query_mcs_log(hid: str, since: str):
    ...

데코레이터 말고 컨텍스트 매니저와 저수준 클라이언트 API도 있다. 기존 코드에 데코레이터를 못 다는 구조면 그쪽을 쓰면 된다.

08 — Harness

Harness — 자가수리 루프

이게 다른 관측 도구들과 갈리는 지점이다. 단순히 "점수가 낮다"를 보여주고 끝내는 게 아니라, 실패를 진단하고 운영 룰을 스스로 쓰고, 그 룰이 실제로 먹히는지 검증까지 한다.

생산측감지턴 종료 → 새 트레이스 채점 → 궤적 게이트 breach 시 상위 티어로 승격 → 진단 노티스 발행
수리측진단별도 repair 에이전트가 노티스·트레이스·기존 룰을 읽고 후보 룰 1개를 작성
검증증명리플레이 + forward trial로 후보 룰을 검증. 못 견디면 폐기
소비측참조다음 턴에 태스크 에이전트가 읽기 전용 툴로 룰을 조회 — 프롬프트에 강제 주입 안 함

설계상 마음에 드는 점

  • ·수리 활동이 태스크 점수를 오염시키지 않는다. repair 에이전트는 자기 모델·자기 세션·자기 트레이스로 돈다.
  • ·룰을 프롬프트에 밀어넣지 않는다. 시스템 프롬프트에 붙는 건 "학습된 룰이 있고 읽는 툴이 있다"는 한 문장뿐. 평가에서 파생된 텍스트가 태스크 프롬프트로 자동 유입되지 않는다.
  • ·워크스페이스가 전부 파일이다. rules.jsonl이 단일 진실원이고 mailbox/, journal.jsonl, evalset/, traces/ 전부 디렉토리에 남는다 — grep으로 감사 가능. 폐쇄망 감사 대응에 유리하다.
  • ·코어 런타임 의존성 0개. 프레임워크 어댑터만 optional extra.
  • ·비용 폭주 방지가 기본값. HARNESS_REPAIR_MODEL을 명시 안 하면 ValueError로 죽는다 — 과금 모델을 임의로 고르지 않는다.

주의 하나. Harness는 태스크가 아니라 턴 단위로 걸어야 한다. 궤적 게이트는 세션당 점수 시계열이 있어야 정체를 감지하는데, 태스크당 한 번만 걸면 샘플이 1개라 아무것도 발화하지 않는다.

09 — Risk

리스크 · 미검증

문서에서 확인 못 한 것과, 확인했지만 걸리는 것을 섞지 않고 나눠 적는다.

확인된 리스크

  • SDKPython·TS SDK 모두 Beta. API 시그니처가 바뀔 수 있다. 버전을 못 박고 반입할 것.
  • 인증AUTH_ENABLED=false는 개발 전용 설계다. 프로덕션 사용은 앞단 인증 프록시가 전제. 이대로 망에 노출하면 안 된다.
  • 신생프로젝트가 젊다. Chirpz AI라는 소규모 팀 산출물이고, 커뮤니티는 Discord 중심. 벤더 지속성 리스크는 있으나 Apache 2.0 + 자체호스팅이라 락인은 없다.
  • 비용채점이 전부 LLM 호출이다. 트레이스 하나당 지표별로 추출·판정 2~3콜. 사내 GPU 사용량을 미리 산정할 것.

반입 전에 반드시 직접 확인할 것

  • □pandaprobe CLI 오프라인 설치 가능 여부 및 self-host 엔드포인트 지정 옵션 — Harness 도입의 전제조건
  • □PostHog·Stripe·Resend·Attio 키 미설정 시 실제로 외부 호출이 0인지 코드/패킷 레벨 확인
  • □frontend(Next.js) 빌드 산출물 반입 가능 여부 — 불가 시 API-only 운영 확정
  • □PostgreSQL 16 / Redis 7이 사내 표준 버전과 호환되는지
  • □LiteLLM이 사내 vLLM 엔드포인트를 openai/ 프리픽스로 정상 인식하는지 (임베딩 포함)
  • □트레이스에 FAB 데이터가 그대로 실린다는 점 — 조건부 트레이싱/마스킹 설정으로 민감 필드 제외 가능 여부
10 — Call

결론

도입 권고 — 단, 1단계 한정으로 먼저.

"에이전트가 대답을 못한다"는 지금 상태로는 고칠 수가 없다. 원인이 프롬프트인지, 툴 스키마인지, 모델 체급인지, 검색이 못 물어오는 건지가 안 갈린 상태라 손댈 곳이 없기 때문이다. PandaProbe의 값어치는 대시보드가 예뻐서가 아니라 그 갈래를 지표로 갈라준다는 데 있다.

그리고 그 1단계 — SDK 계측 —는 폐쇄망 부담이 사실상 없다. 휠 반입 + 데코레이터 몇 줄이고, PANDAPROBE_ENABLED=false 하나로 즉시 무력화되는 롤백 경로가 있다. 서버 자체호스팅과 보안 심의는 baseline 점수를 손에 쥔 다음에 논의하는 게 순서가 맞다.

반대로 Harness는 지금 결정할 사안이 아니다. CLI 오프라인 반입이 확인되기 전까지는 검토 대상에서 빼두는 게 낫다.
