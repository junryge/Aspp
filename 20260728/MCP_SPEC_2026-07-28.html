01핸드셰이크와 세션이 사라졌다

깨짐SEP-2575SEP-2567

이번 개정의 뼈대다. 예전엔 Streamable HTTP로 tool 하나 부르려면 먼저 세션을 맺어야 했다. 서버가 Mcp-Session-Id를 발급하고, 이후 모든 요청이 그 헤더를 들고 다니면서 발급한 인스턴스에 클라이언트를 고정(sticky)시켰다. 이제 그게 없다. 요청 하나가 자기 완결형이라 어떤 인스턴스가 받아도 처리된다.

Before · 2025-11-25세션 필요
① 먼저 세션을 맺는다
POST /mcp HTTP/1.1
Content-Type: application/json

{"jsonrpc":"2.0","id":1,"method":"initialize",
 "params":{"protocolVersion":"2025-11-25",
   "capabilities":{},
   "clientInfo":{"name":"my-app","version":"1.0"}}}

② 응답의 세션ID를 이후 전부 소지
POST /mcp HTTP/1.1
Mcp-Session-Id: 1868a90c-3a3f-4f5b

{"jsonrpc":"2.0","id":2,"method":"tools/call",
 "params":{"name":"search",
   "arguments":{"q":"otters"}}}
After · 2026-07-28단발 요청
한 방에 끝. 어느 인스턴스든 처리 가능
POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: search
Content-Type: application/json

{"jsonrpc":"2.0","id":1,"method":"tools/call",
 "params":{"name":"search",
   "arguments":{"q":"otters"},
   "_meta":{
     "io.modelcontextprotocol/clientInfo":
       {"name":"my-app","version":"1.0"}}}}

capabilities 먼저 알고 싶으면(선택):
Mcp-Method: server/discover

실무 효과: sticky session + 공유 세션 스토어 + 게이트웨이 바디 파싱(DPI)이 필요했던 원격 서버가, 평범한 라운드로빈 LB 뒤에서 그냥 돌아간다. 부가 효과로 tools/list·resources/list·prompts/list가 커넥션별로 달라지지 않으니 캐시가 가능해졌다.

02프로토콜은 stateless, 애플리케이션은 자유 — handle 패턴

패턴 변경

세션이 없어졌다고 앱이 무상태여야 하는 건 아니다. 호출 간 상태가 필요하면 HTTP API가 늘 하던 대로 명시적 handle을 tool이 발급하고, 모델이 그걸 다음 호출의 일반 인자로 되돌려주면 된다.

handle 패턴
① 서버가 핸들 발급
tools/call  create_basket()        → { "basket_id": "bskt_91f2" }

② 모델이 그 핸들을 인자로 되돌려줌
tools/call  add_item(basket_id="bskt_91f2", sku="A-12")

③ 어느 서버 인스턴스가 받아도 처리됨 — 상태가 transport에 숨어있지 않다

메인테이너 쪽 표현으로는 이게 단순한 대체품이 아니라 더 나은 패턴이다. 상태가 transport 메타데이터에 숨는 대신 모델에게 보이는 값이 되니까, 모델이 핸들을 여러 tool에 걸쳐 조합하고 단계 간에 넘길 수 있다.

03MRTR — 서버가 중간에 사용자에게 물어보는 방식이 바뀜

깨짐SEP-2322SEP-2260

stateless인데도 서버는 tool 실행 중간에 사용자 확인(elicitation)을 받아야 할 때가 있다. 예전엔 SSE 스트림을 열어놓고 서버가 elicitation/create, sampling/createMessage, roots/list를 밀어넣는 구조였다. 이걸 Multi Round-Trip Requests로 재설계했다.

흐름

  1. 클라가 tools/call 발행
  2. 서버가 결과 대신 resultType: "input_required" + inputRequests + 불투명 requestState 반환
  3. 클라가 사용자에게 물어 답을 모음
  4. 클라가 원래 호출을 다시 발행 — inputResponses + 받은 requestState를 붙여서
  5. 페이로드에 필요한 게 다 들어있으니 어느 인스턴스가 재시도를 받아도 이어서 처리
InputRequiredResult
{
  "resultType": "input_required",
  "inputRequests": {
    "confirm": {
      "type": "elicitation",
      "message": "Delete 3 files?",
      "schema": { "type": "boolean" }
    }
  },
  "requestState": "eyJzdGVwIjoxLCJmaWxlcyI6WyJhIiwiYiIsImMiXX0="
}

같이 들어온 제약(SEP-2260): 서버가 클라 요청을 실제로 처리하는 중에만 서버발 요청을 낼 수 있다. 예전엔 권고였고 이제 필수다. 사용자가 뜬금없이 프롬프트를 받는 일이 없고, 모든 elicitation은 본인(또는 에이전트)이 시작한 무언가로 추적된다.

참고 stateless로 돌던 서버들이 그동안 elicitation을 못 붙였던 이유가 이거였다. MRTR 덕에 "이 쿼리는 데이터를 지웁니다, 진행합니까?" 같은 사전 확인 게이트를 stateless 서버에서도 표준 방식으로 구현할 수 있게 됐다.

04헤더 기반 라우팅 — 바디 안 까고 라우팅

필수SEP-2243

Streamable HTTP POST에 Mcp-Method(예: tools/call)와 Mcp-Name(예: search)가 필수다. LB·게이트웨이·레이트리미터·WAF가 JSON 바디를 파싱하지 않고 HTTP 레이어에서 라우팅·스로틀·미터링을 한다.

  • 헤더와 바디가 불일치하면 서버가 요청을 거부한다 (에러코드 -32020 HeaderMismatch)
  • MCP-Protocol-Version 헤더도 함께 검증 — 미지원이면 -32022 UnsupportedProtocolVersion
  • tool 파라미터에서 커스텀 헤더를 실어보내는 x-mcp-header 지원 추가
주의 직접 만든 게이트웨이나 리버스 프록시가 세션 어피니티로 붙어있으면, 그 룰을 헤더 라우팅으로 갈아야 한다. 헤더만 넣고 바디는 다른 method를 담는 어설픈 프록시는 그대로 거부당한다.

05리스트 결과가 캐시 대상이 됐다

필수SEP-2549

새 CacheableResult 인터페이스로 두 필드가 필수가 됐다. 모델은 HTTP Cache-Control에서 가져왔다.

필드값의미
ttlMs정수(밀리초)신선도 힌트. 클라가 이 기간 응답을 캐시하고 폴링을 줄인다
cacheScope"public" / "private"공유 중간 계층(프록시 등)이 캐시해도 되는지 여부

적용 대상: tools/list, prompts/list, resources/list, resources/read, resources/templates/list. 기존 listChanged 알림을 대체하는 게 아니라 보완한다. 그리고 리스트에 결정적 순서(deterministic order)가 붙어서, 재접속해도 상위 프롬프트 캐시가 흔들리지 않는다.

보수적인 기본값을 쓰는 SDK도 있다. 예를 들어 TS SDK는 새 리비전을 서빙할 때 두 필드를 항상 내보내되 기본값을 ttlMs: 0 / cacheScope: 'private'(가장 보수적)으로 둔다. 실제 캐시 정책을 광고하려면 서버 옵션으로 명시해야 한다.

06분산 트레이싱 키가 스펙에 고정됐다

신규SEP-414

_meta 안의 W3C Trace Context 전파가 문서화됐고, 키 이름이 못 박혔다 — traceparent, tracestate, baggage. 이미 이렇게 하던 SDK가 여럿이었는데 이제 규격이다. 호스트 앱에서 시작한 트레이스가 클라 SDK → MCP 서버 → 서버가 부르는 하위 시스템까지 따라가서, OpenTelemetry 호환 백엔드에서 하나의 span 트리로 보인다.

07Extensions가 1급 시민이 됐다

신규SEP-2133SEP-1865

2025-11-25에도 확장은 있었지만 절차가 없었다. 이제 공식 틀이 생겼다.

  • 확장은 reverse-DNS ID로 식별 (예: io.modelcontextprotocol/tasks)
  • 클라/서버 capabilities의 extensions 맵으로 네고
  • 독립 ext-* 저장소 + 위임 메인테이너, 스펙과 따로 버저닝
  • SEP 프로세스에 Extensions Track 신설 — 실험 → 공식 경로

MCP Apps (SEP-1865) — 서버가 렌더링하는 UI

서버가 인터랙티브 HTML 인터페이스를 내려주고, 호스트가 샌드박스 iframe에 렌더한다. tool이 UI 템플릿을 미리 선언하니 호스트가 프리페치·캐시·보안 리뷰를 실행 전에 할 수 있다. 렌더된 UI는 MCP의 동일한 JSON-RPC 기반 프로토콜로 호스트와 대화하므로, UI에서 시작된 액션도 직접 tool 호출과 같은 감사·동의 경로를 탄다.

공식 확장으로 Enterprise Managed Authorization(EMA)도 함께 언급된다.

09인증(Authorization) 하드닝 — 6개 SEP

필수DCR 폐지예정

메인테이너들이 "구현자들이 시간을 가장 많이 쓰는 지점"으로 꼽은 영역. OAuth 2.0 / OpenID Connect 실제 배포 관행에 맞췄다.

SEP변경내용 / 이유
2468RFC 9207 iss 검증인증서버가 iss를 돌려주고, 클라는 code 교환 전에 검증해야 한다. MCP의 "클라 1 : 서버 다수" 배포 패턴에서 흔한 mix-up 공격을 막는다. 향후 버전에서는 iss 없는 응답을 거부하게 될 예정
837application_type 선언DCR 때 OIDC application_type을 명시. 인증서버가 데스크톱/CLI 클라를 "web"으로 기본 처리해서 localhost redirect를 거부하던 문제 해결(그 redirect_uri 에러의 정체)
2352issuer 바인딩등록 자격증명을 발급한 인증서버 issuer에 묶는다. 서버 간 재사용 금지. 리소스가 다른 인증서버로 옮겨가면 재등록
2207refresh tokenOIDC 스타일 인증서버에서 refresh token 요청하는 방법 문서화
2350scope 누적step-up 시 스코프 누적 규칙 명확화
2351.well-known디스커버리 suffix 규칙 명확화

DCR → CIMD: Dynamic Client Registration이 공식 폐지 예정이 됐고, Client ID Metadata Documents(CIMD)가 표준 방향이다. DCR은 하위호환으로 계속 동작하지만 향후 버전에서 제거된다.

11Tool 스키마 확장과 에러코드 정리

신규깨짐SEP-2106SEP-2164

JSON Schema 2020-12 전체 지원 (SEP-2106)

  • tool의 inputSchema/outputSchema가 full JSON Schema 2020-12로 승격
  • input은 루트 type:"object" 제약은 유지하되, 조합(oneOf/anyOf/allOf)·조건부·참조($ref/$defs) 허용
  • output 스키마는 제약 없음. structuredContent가 객체만이 아니라 아무 JSON 값이어도 됨
  • 외부 $ref URI 자동 역참조 금지, 스키마 깊이·검증 시간에 상한을 둘 것

-32020HeaderMismatch — 헤더와 바디 불일치
-32022UnsupportedProtocolVersion

추가로 모든 result에 resultType 필드가 필수다. 일반 결과는 "complete", MRTR 중간 응답은 "input_required".

12앞으로 이렇게 안 깨지게 하려고 만든 장치

신규SEP-2596SEP-2484SEP-1777
  • Feature lifecycle 정책 — 모든 기능에 Active → Deprecated → Removed 단계. 폐지 후 제거까지 최소 12개월
  • Extensions 프레임워크 — 신규 기능은 opt-in 확장으로 먼저 나와 안정화, 그 다음에(필요하면) 스펙 편입
  • Conformance suite 게이트 — Standards Track SEP는 conformance 스위트에 해당 시나리오가 들어가야 Final이 될 수 있다(SEP-2484). 이 스위트가 새 SDK tier 시스템의 채점 기준이기도 하다

메인테이너 입장은 명확하다: stateless 개편은 한 번의 깔끔한 단절이 필요했고, 이걸 넘긴 다음부터는 2026-07-28을 타깃으로 만든 구현이 transport·lifecycle 코드를 다시 안 쓰고 이후 리비전을 흡수할 수 있게 하는 것이 목표다.

14우리 MCP 서버(8010) 영향도 체크

구분 위 13개 섹션은 공식 스펙/블로그에 나온 사실이고, 이 섹션은 우리 구성(Python · streamable-http 8010 · Oracle read-only Phase 1 · Phase 2 제어는 staging table + HITL 게이트 · 폐쇄망)에 대입한 판단이다.

결론부터

지금 급하지 않다. 2025-11-25로 운영 유지하고, 브랜치에서 마이그레이션 하는 게 맞다. 이유는 세 개다 — ① 발행일이 스위치오프가 아님, ② 폐지 기능 유예 최소 12개월, ③ 폐쇄망이라 클라도 우리가 통제한다(외부 신 클라가 갑자기 붙는 리스크가 없음).

영향 큰 것

오히려 이득

  • Phase 2 HITL 게이트가 표준화된다. "이 명령 실행합니까?"를 MRTR input_required로 프로토콜 레벨에서 받는다. 지금은 staging table + 별도 승인 흐름으로 우회하고 있는데, 그중 사용자 확인 단계는 표준 elicitation으로 흡수 가능하다. 승인 이력·감사 로그는 그대로 유지.
  • handle 패턴이 우리 staging table 구조와 궁합이 맞다. 명령 등록 → command_id 반환 → 이후 조회/승인/취소가 그 ID를 인자로 받는 형태. 이미 그 모양으로 설계돼 있으니 세션 제거 영향이 작다.
  • 수평 확장 여지. 지금은 단일 인스턴스라 체감이 없지만, 나중에 이중화할 때 sticky·세션 스토어를 안 만들어도 된다.

영향 없거나 작은 것

  • Sampling — 모델 호출을 서버가 직접 하는 구조면 애초에 안 쓰고 있다. 영향 0.
  • Roots — DB 조회 tool 파라미터로 스코프를 넘기는 구조면 영향 0.
  • Logging — MCP logging capability를 안 쓰고 파일/JSONL 감사 로그를 쓰고 있으면 영향 0. 폐지 대체 권고도 stderr/OTel이라 방향이 같다.
  • Tasks — 실험적 Tasks API를 안 썼으면 무관.
  • OAuth 하드닝 — 폐쇄망 내부 인증이면 대부분 비해당. 다만 나중에 사내 SSO를 붙일 때 iss 검증·CIMD 방향은 미리 알고 있어야 한다.
  • Oracle 커넥션 풀 — 프로세스 레벨이라 프로토콜 세션 제거와 무관. thin 모드 그대로.
  • MCP Inspector — Node/npx 없는 환경이라 여전히 못 쓴다. Python 클라이언트로 검증하는 방식 유지.

순서

  1. 운영은 2025-11-25 그대로 고정. 상한 핀 걸어서 의도치 않은 v2 업그레이드 차단
  2. 브랜치 하나 따서 mcp v2 wheel 반입 → 리네임 → read-only tool부터 기동
  3. Python 클라이언트로 스모크: server/discover, tools/list(+캐시 필드), tools/call, 헤더 불일치 거부, DELETE/DROP 가드가 isError로 제대로 올라오는지
  4. MRTR 확인 게이트를 Phase 2 제어 tool 하나에 시범 적용
  5. 스펙 폐지 대상(-32002 매칭, roots/sampling/logging)에 새 의존성 만들지 않기
